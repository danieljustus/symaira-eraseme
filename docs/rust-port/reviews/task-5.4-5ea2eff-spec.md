## Findings

1. **`docs/rust-port-contract-matrix.md`'s DOM-009 row was not updated — still lists "legacy-Python detection" as TODO after this slice completes it.** Severity: Medium. The immediately prior slice on this same task (`f0a96ce2`, PR #907) established the working convention: it edited the DOM-009 row from plain `TODO` to `PARTIAL (PASS: Generate/WriteFiles …; TODO: Install/Uninstall/Status, legacy-Python detection, native macOS/Linux/Windows execution of the Windows-specific traversal test)`, explicitly enumerating the three remaining sub-items. This commit (`5ea2eff`) completes one of those three enumerated items — legacy-Python detection — but leaves the row's text completely unchanged; `docs/rust-port-contract-matrix.md` still reads "TODO: Install/Uninstall/Status, legacy-Python detection, …" verbatim after this commit. The matrix is the authoritative cross-task tracking artifact for the whole migration (referenced from `AGENTS.md`/the plan doc); leaving it stale means a reader relying on it alone would not know this sub-item is done, breaking the per-slice-update precedent this exact task established one commit ago. Fix: update the DOM-009 row to move "legacy-Python detection" from the `TODO:` clause into the `PASS:` clause, citing this commit.
2. **Unicode case-folding divergence between Go's `strings.ToLower` and Rust's `to_lowercase()` for U+0130 (LATIN CAPITAL LETTER I WITH DOT ABOVE).** Severity: Low. Empirically confirmed, not just theoretical: Go's `strings.ToLower` uses Unicode's *simple* (one-rune-to-one-rune) case mapping, so `"SİTE-PACKAGES"` (Turkish dotted capital İ) lowercases to `"site-packages"` (İ → `i`, the dot is dropped) — the `site-packages` marker matches (`strings.Contains(lower, "site-packages") == true`). Rust's `str::to_lowercase()` uses the *full* Unicode default case-conversion algorithm (`SpecialCasing.txt`'s unconditional İ→`i`+combining-dot-above (U+0307) mapping), producing `"si\u{307}te-packages"` — an extra codepoint is inserted that breaks the contiguous ASCII substring, so `.contains("site-packages")` returns `false` where Go returns `true`. Verified independently in this review with a standalone `go run` and `rustc` repro (see commands table). This affects the `python`, `site-packages`, and `venv/bin/activate` markers (each contains a lowercase `i`) whenever content contains U+0130 positioned to form one of those words. Not currently reachable — nothing calls `is_python_scheduler_content` with attacker/locale-supplied content yet, and no fixture covers non-ASCII input — but it is a genuine, verified break from "byte-exact parity" for realistic (if rare) non-ASCII unit-file content, worth a regression fixture case (and likely a manual Unicode-aware fold, e.g. via `unicode_casefold`-style simple mapping, or acceptance of the divergence with a documented rationale) before this path is exposed to untrusted or locale-varied input.
3. **`fs::read` + `String::from_utf8_lossy` vs Go's `os.ReadFile` + `string(data)` diverge on invalid-UTF-8/binary content.** Severity: Low. Go strings are raw byte sequences — `strings.Contains`/`strings.ToLower` on invalid UTF-8 still perform correct byte-level substring matching against the ASCII marker literals, since Go's `ToLower` passes undecodable bytes through unchanged. Rust's `String::from_utf8_lossy` unconditionally replaces each invalid byte sequence with U+FFFD (3 UTF-8 bytes) *before* any marker matching happens; if a marker word happened to straddle an invalid-UTF-8 byte boundary in the source file, Go could still match it byte-for-byte while Rust's replacement would break the match (and, less plausibly, the reverse — replacement bytes coincidentally forming an ASCII pattern Go wouldn't see as such — is not possible here since U+FFFD's UTF-8 encoding contains no ASCII bytes). No fixture exercises non-UTF-8 content, and no current caller can feed arbitrary/binary paths to these functions, so this is presently unreachable — but it is a real representational gap against the stated "byte-exact" contract, worth a fixture case (deliberately malformed-UTF-8 content adjacent to a marker) once these functions gain external callers that might see non-text input.
4. Platform-parameter type change — reviewed, non-issue for this slice. Go's `ScanLegacyPythonUnits(home string, platform Platform)` lowercases its `platform` argument and, if the result is a *non-empty but unrecognized* string, silently falls through its `switch`'s `default:` arm and returns `nil, nil` (i.e., treated the same as if no native units existed) rather than erroring or autodetecting. Rust's `scan_legacy_python_units(home: Option<&str>, platform: Option<Platform>)` cannot represent "unrecognized platform" at the type level at all — a `None` (e.g., from a failed `Platform::parse`) falls through to `detect_platform()` autodetection instead, which is a different outcome than Go's silent-empty-result behavior for that specific case. However, Go's only production caller of `ScanLegacyPythonUnits` (`Install`, not yet ported) already rejects unrecognized platform strings via `isSupported(platform)` *before* ever calling it, so this Go branch is dead code on every real call path; no Rust caller exists yet that could observe the difference either way. Flag for the future `Install` slice: when wiring a raw `--platform` CLI flag through `Platform::parse`, decide explicitly what an unparseable value should do (error, matching `isSupported`'s intent, not silent autodetect) rather than defaulting through the `None` arm.
